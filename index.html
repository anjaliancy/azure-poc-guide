    Part 1

    What a proof of concept is

    A POC answers one question: is this idea worth investing in? It is not a small version of the finished product.

    POC, pilot, production

    POC

    Weeks, fake data. Built to be judged, then kept or dropped.

    Pilot

    Real users and data, limited scope, with support. Only after a POC says yes.

    Production

    Everyone, full security, an owner on call. A project, not an experiment.

    The rule that keeps it smallIf a feature doesn't help answer the question, it goes on the "not now" list.

    Six decisions

    Write these down before any work starts.

    In / out of scopeIn: request, approve, summary. Out: payroll link, mobile app

    Part 2

    Ideation: find the right problem

    Most failed POCs solve the wrong problem. Listen first, define second, build third.

    Who to talk to

    The doers

    Know the real steps. HR admins.

    The users of the output

    Show what's actually needed. Managers.

    The owner

    Defines success and limits. Head of HR.

    IT and risk

    Can stop you late if skipped early. Data protection, cloud team.

    Aim for 6 to 10 conversations of 30 minutes. After about five on one theme you mostly hear repeats.

    Interview well

    • Ask about the last time, not "usually". Facts beat tidy stories.
    • Listen for workarounds. A personal spreadsheet is an unwritten requirement.
    • Ask to see the real files.
    • Don't pitch your idea. People then answer politely, not honestly.
    • Two people: one asks, one writes. Play it back within a day: "what did I get wrong?"

    Question bank

    1. Walk me through the last time you did this, start to finish.
    2. Which step is slowest? Which do you dread?
    3. Where do mistakes happen, and what did the last one cost?
    4. What do you keep outside the official system, and why?
    1. What decision do you make with this? When do you need it?
    2. What do you do when it's late or looks wrong?
    3. What would make you trust it more?
    4. What must never be shown to others?
    1. What would make you say "worth it" in six months?
    2. What does the problem cost today (time, money, risk)?
    3. What must not change? Who else must be on board?
    4. What would make you stop?
    1. What data may a POC hold, and where?
    2. Which regions, tags and naming rules are mandatory?
    3. Which sign-in method must we use?
    4. Who owns the system after the POC?

    Make sense of it

    1Five whys

    Ask "why?" until you reach a cause you can act on.

    2Map the journey

    One row per step: who, pain, evidence (a quote or number).

    3"How might we…"

    Turn each pain into an open question.

    4One-sentence problem

    Test it on two interviewees. If they don't nod, keep going.

    Prototype and test

    Paper or slides

    Sketch screens; walk someone through.

    Clickable mock-up

    Linked slides. Good for layout and wording.

    "Wizard of Oz"

    Looks real; a person does the work behind it. Tests the idea before the engine.

    Working thin slice

    The real thing, minimal, with fake data.

    • Test with 3 to 5 people. Give a task, then stay quiet.
    • Where they hesitate, the design needs work.
    • Write findings in their own words.

    Work as a team

    • One-page brief everyone has seen (template below).
    • Weekly 20-minute show-and-tell. Show what works; no slides.
    • Decision log: date, decision, why, who. Ends "I thought we agreed…".
    • Say "that's for later" kindly: "Great idea. It's on the next-version list."
    • Agree who decides scope changes and signs off the demo.

    Technical detail

    From brief to data model

    Nouns become tables; states become a rule table. LeaveLoop: employees, leave_requests (status, decided_by, decided_at, reason), audit_log.

    • Key by what makes a record unique, usually unit and period, or next year overwrites this one.
    • Constraints in the database (CHECK, UNIQUE, foreign keys) catch what code misses.
    • Rule table first: (from, to) → roles and state → role → fields. Enforce on the server.
    • Review the schema with a human before any screen. It's the costliest thing to change later.

    Part 5

    Getting access, early

    The usual reason a POC slips isn't the building. It's waiting for permission.

    Three levels of permission

    1Create things

    Web app, database, storage. Usually granted for one project folder.

    2Let things talk safely

    Allow the app to open the safe without a password. IT guards this.

    3Organisation-wide

    Switching on services for the whole subscription. Very few people.

    A POC can start with level 1 and fake data. Levels 2 and 3 are needed before anything real.

    Time-limited accessSome roles last only hours and must be re-activated. If it worked this morning and fails now, re-activate it.
    Technical detail
    To do thisYou need
    Create resourcesContributor on the resource group
    Create role assignmentsOwner, User Access Administrator or RBAC Administrator
    Write Key Vault secrets / blob dataKey Vault Secrets Officer; Storage Blob Data Contributor
    Register resource providersContributor/Owner at subscription level
    Microsoft Graph (az ad)Allowed by conditional access
    az login
az account set --subscription "<id or name>"
az account show -o table      # confirm tenant and subscription first

    Tools: Azure CLI, Git, Node 20+, your runtime. Open a new terminal after installing. If database tokens are blocked on your laptop, use the in-app setup in Part 7. If Graph is blocked, read your object id from the oid claim of your ARM token.

    Part 6

    Building it: the order that works

    Foundations first. Each step ends with something a non-technical colleague can review.

    Seven steps

    1The records

    What's stored and how it relates. Review with the subject lead; hardest to change later.

    2The rule book

    Who may do what, in which state. One place the whole system obeys.

    3The history

    Every change: who, what, before, after, when. Nothing silently overwritten.

    4Who is who

    Simple sign-in for the POC, shaped so a proper one can replace it.

    5The main journey

    The thin slice, then other roles.

    6Safety nets

    Automatic tests for rules that would quietly corrupt data, including that forbidden actions are refused.

    7Demo data

    Invented data covering every state, so any reviewer sees every screen in a minute.

    Rules live on the serverHiding a button is courtesy, not security. Anyone can call the system directly, so the system itself must refuse what isn't allowed.
    Deploy an empty skeleton in week onePermission, region and policy problems show up early, not the night before the demo.
    Technical detail
    1. Schema first (SQLite locally, Azure SQL in cloud). Portable SQL (? placeholders, no ON CONFLICT/MERGE), one file that knows dialect differences, a test that fails if schema files drift.
    2. Rule table: TRANSITIONS: (from, to) → roles; EDITABLE: state → role → fields. 403 for role problems, 409 for state problems.
    3. Audit: one row per changed field, in the same transaction; write nothing if nothing changed. Append-only (ledger table on Azure SQL).
    4. Auth: signed, expiring tokens; routes depend only on current_user and require_roles, so Entra ID can replace the login.
    5. Tests: rules, permissions (including must-be-refused), calculations. Run on every change.
    6. Seed: idempotent, gated by SEED_DEMO_DATA, only on an empty database.
    7. Operations: /health and /health/db from day one; config in environment variables.
    Part 7

    Putting it on Azure, in two stages

    First get something clickable this week. Then make it properly secure. Don't skip stage 1; don't mistake it for stage 2.

    Two stages

    Stage 1 · Demo

    A public link to click.

    • Fake data only
    • Shared simple login
    • Data in a file on the web app
    • Secrets as settings

    For: feedback and first demo.

    Stage 2 · Proper

    Safe enough for real information.

    • Managed database with history
    • App signs in with its own identity
    • Secrets in a vault
    • Monitoring and a tested backup

    Needed before: real data or users.

    Stage 1: demo

    In plain terms: create a project folder, rent a small server for the back office, create a free place for the screens, give the back office its settings, upload the code, build the screens pointing at it, upload them, check the health page says OK, try each role.

    Technical detail

    Variables

    $RG   = "rg-leaveloop-poc"
$LOC  = "<approved region>"
$PLAN = "plan-leaveloop-poc"
$APP  = "app-leaveloop-poc-<unique>"   # becomes <APP>.azurewebsites.net, globally unique
$SWA  = "swa-leaveloop-poc"

    1 · Group and plan

    az group create -n $RG -l $LOC --tags CostCenter=<code> Owner=<you>
az appservice plan create -g $RG -n $PLAN --is-linux --sku B1

    2 · Static Web App and token

    az staticwebapp create -g $RG -n $SWA -l <swa region> --sku Free
$swaHost  = az staticwebapp show -g $RG -n $SWA --query defaultHostname -o tsv
$swaToken = az staticwebapp secrets list -g $RG -n $SWA --query properties.apiKey -o tsv

    The token is a password. Don't commit it.

    3 · The API web app

    az webapp create -g $RG -p $PLAN -n $APP --runtime "PYTHON:3.12"
az webapp config set -g $RG -n $APP --startup-file "bash startup.sh"
az webapp config appsettings set -g $RG -n $APP --settings `
  SCM_DO_BUILD_DURING_DEPLOYMENT=true ENABLE_ORYX_BUILD=true `
  "SECRET_KEY=<long random string>" "ALLOWED_ORIGINS=https://$swaHost"

    ENABLE_ORYX_BUILD=true makes App Service install requirements during a zip deploy. Without it: 503.

    4 · Deploy the API

    Zip with code, requirements.txt and the startup script at the root, forward-slash paths, LF line endings. Build it with a script (Python zipfile), not Compress-Archive.

    az webapp deploy -g $RG -n $APP --src-path ./deploy.zip --type zip --async true
# poll https://$APP.azurewebsites.net/health (first start installs packages: a few minutes)

    5 · Build and publish the front end

    cd frontend
$env:VITE_API_URL = "https://$APP.azurewebsites.net/api"   # baked in at build time
npm ci
npm run build
npx --yes @azure/static-web-apps-cli deploy ./dist --deployment-token $swaToken --env production

    Anything with a VITE_ prefix ships to every browser: no secrets. Search the bundle for the host name to confirm it points where you meant.

    6 · Verify

    • GET /health OK; sign in as each role; one allowed and one forbidden action.
    • Browser network error but curl works: check CORS (ALLOWED_ORIGINS must hold the exact front-end URL).
    az webapp log config -g $RG -n $APP --docker-container-logging filesystem
az webapp log tail   -g $RG -n $APP

    For a throwaway demo, keep SQLite on the web app's persistent /home disk. It doesn't survive scaling to several instances, so move to Azure SQL once the data matters.

    Stage 2: proper

    What changes: a managed database is created; an administrator sets up its tables once; the app is allowed to read and write rows but not change the structure; secrets move to a vault; demo shortcuts are removed.

    Technical detail
    • Entra-only authentication on the SQL server: no SQL logins exist.
    • A named person (ideally a group) is SQL admin.
    • The API's managed identity is a database user with read/write on tables only.
    • Optional ledger audit tables: WITH (LEDGER = ON (APPEND_ONLY = ON)). Tampering becomes detectable, not impossible.

    One-off table setup

    A, from your machine (if developer machines may get database tokens): add your IP to the firewall, az login --scope https://database.windows.net/.default, run setup as admin, create the API's user, remove the firewall rule.

    B, from inside the web app (when conditional access blocks A):

    1. Make the app's identity the temporary SQL admin (management call, no database sign-in): 
      az sql server ad-admin create -g $RG -s <sql server> --display-name $APP --object-id <app principal id>
    2. Run setup at start, controlled by e.g. SETUP_MODE=real: create tables, seed reference data, grant the identity read/write. If FROM EXTERNAL PROVIDER fails ("Server identity is not configured"), create the user from the identity's client id (CREATE USER [name] WITH SID = ..., TYPE = E).
    3. Watch the setup log until it succeeds.
    4. Restore the human admin, delete the setup settings, restart.
    5. Confirm /health/db reports the Azure SQL database.

    Rehearse on a throwaway database named *_test, and make any destructive reset refuse to run elsewhere. Connect with ActiveDirectoryMSI on Azure (ActiveDirectoryDefault locally). With no server configured, fall back to SQLite.

    Secrets and templates

    Technical detail
    StageWhere secrets live
    LocalEnvironment variables or untracked .env
    Demo, fake dataApp settings, typed by the owner, never in the repo
    Anything realKey Vault, referenced from app settings

    Reference syntax: @Microsoft.KeyVault(VaultName=<vault>;SecretName=<name>); the app's identity needs Key Vault Secrets User. Verify it resolved, or the app silently uses the literal text as its secret:

    az rest --method get --url "https://management.azure.com/subscriptions/<SUB>/resourceGroups/$RG/providers/Microsoft.Web/sites/$APP/config/configreferences/appsettings?api-version=2022-03-01" --query "value[].{setting:name,status:properties.status}" -o table

    If it shows AccessToKeyVaultDenied after the role exists, re-run the same deployment (it re-saves settings); a restart may not help.

    Infrastructure as code (Bicep)

    az deployment group what-if -g $RG -f main.bicep -p poc.bicepparam   # lists changes, makes none
az deployment group create  -g $RG -f main.bicep -p poc.bicepparam
    • Names from a prefix, the environment and a short hash of the resource group id.
    • Same tags on everything via one parameter; no secrets in parameter files.
    • Guard role assignments with a switch (createRoleAssignments) so it still deploys when you may not create them.
    • Look up role ids: az role definition list --name "Key Vault Secrets User" --query "[].name" -o tsv.
    • What-if can't see quota limits; if a size or region fails, change the parameter and re-run.
    Part 8

    Keeping it safe

    A POC with fake data can be simple. The habits you form now decide how easily it grows up.

    Principles

    Least access

    Everyone and everything gets only what it needs.

    No secrets in the open

    Never in code, chat, slides or tickets. The owner types it in.

    The system enforces the rules

    Not the screen.

    Keep a record

    Every important change: who, what, when.

    "Tamper-evident"Like a seal on a jar: it doesn't stop someone opening it, but you can tell if they did. Works best with tight limits on who can write at all.
    Technical detail: POC baseline
    • HTTPS only, TLS 1.2, FTPS off, health check set.
    • Roles enforced on the server by role and workflow state; tests for refusals.
    • Audit log in the same transaction; ledger on audit tables.
    • Managed identity for Azure-to-Azure access.
    • Storage private, no shared keys; uploads limited by size and an allow-list (never executables or HTML).
    • Front-end build variables are public: no secrets.

    Before real data

    ItemWhy
    Company sign-in (and a plan for outside partners)Replace shared passwords
    Secrets in a vault, access by roleNo secrets in settings
    Database off the public internetRemove the public path
    Edge protection, proper address (by policy)Defence at the front door
    Locked storage for change-history proofsMakes tamper-evidence credible
    Files in private storage, limited-time linksOut of the database; versioned
    Cross-region backups, a restore you've testedRecovery
    Owner, runbook, alertsSomeone is responsible
    Data classification approvedCompliance
    Technical detail: hardening
    • Entra ID sign-in (external tenant for partners).
    • Private endpoints or restricted SQL firewall; remove "allow Azure services".
    • Front Door with WAF; custom domain.
    • Time-based immutability policy on the ledger digest container.
    • Blob uploads via short-lived links; geo-redundant backups; staging slot (Premium plan).
    Part 9

    Show it, judge it, decide

    A POC exists to be judged. Plan the demo and the decision as carefully as the build.

    The demo

    1. The question in the sponsor's words, and the agreed success measures.
    2. The old way in 60 seconds, with a real example of the pain.
    3. Walk the thin slice as each role, in the order a request travels.
    4. Show the history. Often what wins trust.
    5. Show a refusal: someone trying something not allowed.
    6. Let a real user drive.
    7. Finish with the measures, what's unknown, and your recommendation.

    Keep a recording as a fallback.

    Decision paper (1 to 2 pages)

    • The answer: yes, no, or not yet.
    • Evidence against each success measure, plus users' own words.
    • What running it for real takes: people, cost range, risks, owner.
    • Options: stop, extend, pilot, or build for production.
    • Recommendation and the decision needed, with a date.
    Technical detail: monitoring and teardown 
    requests   | where success == false | summarize count() by name, resultCode, bin(timestamp, 1h)
exceptions | order by timestamp desc | take 50
    • Alerts: health check failing, HTTP 5xx, database CPU/DTU over 80%.
    • Budget alert set; tags on every resource.
    • Teardown: az group delete -n $RG removes everything inside. Check the name twice. Key Vault soft delete keeps the vault name reserved for its retention period.

    When things go wrong

    Most problems are common and have known causes.

    Symptoms

    What you seeUsual reason → what to do
    "I can't create this"Permission or policy limit → ask IT (Part 5)
    Worked this morning, "access denied" nowTime-limited access expired → re-activate
    Error right after uploadServer still starting or misconfigured → wait a few minutes, check the health page
    Screens load, nothing savesScreens and back office not connected → check address and allowed origins
    Bill higher than plannedSomething left running → list by cost; scale down or delete
    Everyone wants one more featureScope creep → "won't this time" list, decision log
    Testers don't use itWrong problem → back to Part 2, re-interview

      Reference

      Glossary

      API
      The back office: applies the rules and talks to the data.
      Audit log
      Record of every important change: who, what, before, after, when.
      Azure
      Microsoft's cloud: rentable computing, storage and services.
      Bicep
      A text file describing the cloud resources you want, so they can be recreated.
      CORS
      Browser rule about which web addresses may talk to the back office.
      Entra ID
      Microsoft's company sign-in service.
      Key Vault
      A safe for passwords and keys.
      Ledger
      Database feature that makes after-the-fact changes to history detectable.
      Managed identity
      A badge the app itself holds, so no stored password.
      MoSCoW
      Must, Should, Could, Won't: a way to rank features.
      POC
      Proof of concept: a small, time-boxed test of whether an idea is worth pursuing.
      Resource group
      A folder holding everything for one project in Azure.
      Role (RBAC)
      A named set of permissions for a person or app.
      SKU
      The size or tier of a service; sets capability and price.
      Tag
      A label on a resource, such as owner or cost centre.
      Thin slice
      The smallest complete path through the system, built first.
      WAF
      Web application firewall: filters harmful traffic before it reaches the app.
